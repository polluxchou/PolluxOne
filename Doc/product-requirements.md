# Pollux One — 产品需求文档

版本：当前主干 + `teleprompter-fixed-window-pacing`（PR #2）
日期：2026-09-04
状态：iOS 端功能可跑通并有离线验证；真机语音链路未验证

---

## 1 · 产品定位

**先是一台相机，其次才具备智能提词能力。**

Pollux One 不是"带相机的提词器"，而是"带提词能力的相机"。这个顺序决定了每一处
取舍：画面永远是主体，HUD 是薄薄一层；任何会挤占画面或把用户视线拉离镜头的
设计都不做。

所有工程与设计决策只检查一个问题：

> **这件事能帮说话的人保持与镜头的眼神接触吗？**

答案为否的功能不做，答案为否的状态要明确告知用户（见 §4.1 后置镜头警示）。

## 2 · 核心问题

传统提词器把"读稿"这件事解决得很好，却制造了一个更大的问题：**为了看字，
眼神必须离开镜头**。观众能立刻感觉到这一点，哪怕说不出原因。

第二个问题是**速度**。定速滚动的提词器要求人去适应机器：读快了要等，读慢了
要追。真实的说话有停顿、有临场加词、有口误重说，定速滚动对这些一律无能为力。

Pollux One 对这两个问题的回答：

1. 提词内容贴近前置摄像头 / Dynamic Island 放置，视线偏移量压到最小。
2. 提词位置**跟随实际朗读位置**，由语音识别驱动，而不是按固定速度滚动。

## 3 · 目标用户与场景

| 用户 | 场景 | 对产品的核心要求 |
|---|---|---|
| 口播创作者 | 一人一机，对着前置镜头念稿，一条过 | 眼神接触、跟得准、改稿不用停机 |
| 需要出镜的专业人士 | 产品演示、课程录制、公司内部视频 | 稿子长、术语多、要能中途改词 |
| 双语创作者 | 中英文稿交替 | 两种语言都要排版正确、识别正确 |

**不面向**：需要多机位/导播的团队拍摄；需要在 App 内写长稿的用户（长文本编辑在
Web 端，见 §4.6）。

## 4 · 功能需求

### 4.1 相机（主体）

相机能力对齐 iOS 原生相机的常用档位，不做摄影玩法的扩展。

| 项 | 当前支持 | 说明 |
|---|---|---|
| 镜头 | 超广角 / 广角 / 长焦，按机型实际能力显示 | 档位标签（`.5 · 1× · 5`）按设备上报的构成镜头算出，不硬编码 |
| 分辨率 | 1080p / 4K | |
| 帧率 | 24 / 30 / 60 fps | |
| 曝光 | EV 补偿滑杆，范围取设备上报值 | |
| 对焦 | AUTO / LOCK | 点按画面对焦并测光 |
| 前后切换 | 支持，**录制中禁用** | 切换会移除并重加视频输入，正在写的影片文件会被提前结束 |
| 格式切换 | 支持，**录制中禁用** | 同上，重配 active format 会中断文件写入 |

**后置镜头警示（必需）**：切到后置时 HUD 必须显式标出「提词器已不在镜头方向上」。
这是整个产品里唯一一个"眼神接触"答案为否的状态，与其静默降级，不如告诉用户——
一条拍坏的素材现在修比回放时修便宜。

**剩余可录时长**：HUD 常驻显示，按当前分辨率/帧率与可用空间估算。

### 4.2 提词器显示（当前版本重点）

**固定行窗**。提词块的行数固定，不随句子长短变化：

| 语种 | 可见行数 | 已读暗行 | 衬底位置 | 未读行 |
|---|---|---|---|---|
| 中文 | 5 | 第 1 行 | **第 2–3 行** | 第 4–5 行 |
| 拉丁 | 6 | 第 1–2 行 | **第 3–4 行** | 第 5–6 行 |

需求要点：

- **衬底位置绝对固定。** 读者的视线有一个恒定落点。文字从衬底上方滑过，衬底本身
  不动。
- **衬底永远盖住两个完整行。** 不允许出现半行截断。
- **整行吸附推进。** 每次前进一整行，走一次约 0.3 秒的缓动。行内的连续感由字级
  高亮承担，而不是靠像素级滚动——像素滚动会让圆角衬底边缘出现半行，视觉更脏。
- **行内进度用字级高亮体现。** 当前行的已读部分覆一层更深的青铜色，边界按每个
  字符的实测位置定位。
- 脚本开头/结尾时，衬底位置**不移动**，靠上下补空行实现。

**排版正确性（中文特有）**：

- 行首不出现 `。，、；：！？）」` 等收尾标点（行首禁则）
- 行尾不出现 `（「《` 等起始标点（行尾禁则）
- **中文稿里内嵌的英文词不能被腰斩**。中文稿夹英文是常态（产品自己的示例脚本
  就是 `"Pollux One 从另一个问题出发。"`）。
- 拉丁文不在词中间断行。

**可调项**（点按提词文字进入临时调节模式，不做常驻滑杆——常驻竖滑杆会和曝光
滑杆撞位置）：

| 项 | 范围 | 说明 |
|---|---|---|
| 位置 | ±60pt | 上下微调 |
| 字号 | 15–28pt | 中文自动降一档并放宽行高（CJK 字身更大，套拉丁行距会显得挤） |
| 宽度 | 0.5–1.0 | 改宽度会实时重新断行 |
| 不透明度 | 0.3–1.0 | |

**右侧进度轨**：显示整篇读到哪了，并用方括号标出衬底那两行。刻意不显示百分比
数字——位置本身就是读数。

### 4.3 语音跟随

提词位置由语音识别驱动。需求按"真实的人怎么说话"定义，而不是按理想朗读：

| 行为 | 要求 |
|---|---|
| 顺序朗读 | 跟住 |
| **只念了半句就要跟上** | 念到一句的前几个词，提词器就要移到这句——这是最核心的行为 |
| 重复一句 | 保持不动，不能往前跳 |
| 跳过一句 | 跟上 |
| 往回重念 | 跟回去 |
| 口语化改写 / 临场加词 | 不丢位置 |
| 念错后重说 | 跟住重说的那一遍 |
| 识别结果没有标点 | 照样对齐（ASR 常态） |
| 无关说话 / 噪音 / 咳嗽 | **位置不动，也不能往后退** |
| 长时间停顿 | 停在原处，不能继续滚 |

**速度必须参考用户实际阅读速度。** 语音识别有 0.3–0.8 秒延迟，两次结果之间如果
什么都不做，屏幕上就是一段死寂然后一次跳变。所以：

- 从实际朗读进度测出"字/秒"，做指数平滑
- 两次识别结果之间按这个速度匀速前推
- 识别结果回来后，小偏差滑行吃掉、大偏差判为跳读直接跳到位

**安全约束（必需）**：前推必须有上限，封在最后一次确认位置的前方约一行多。没有
这个上限，读者停下来喝口水就会被匀速推到脚本末尾。读者一停，行内高亮随之停住——
这个"停住"本身就是给读者的反馈，不需要额外提示文案。

**识别失败要说清楚**：麦克风或语音权限被拒、识别启动失败时，HUD 要明说是哪一种。
一个不动的提词器和一个坏掉的算法在屏幕上长得一模一样。

### 4.4 安全词与语音改稿

录制中发现稿子有问题，不应该被迫停机重来。

- 说出安全词（默认 `Pollux`）唤醒指令模式
- 说出改稿指令（如「把这段改成…」/ `change this paragraph to…`）
- **必须确认后才生效**，不自动改稿
- 指令只解析安全词**之后**的话——稿子正文里出现过触发词不能误触发
- 同一次说话被识别器反复上报，只触发一次（冷却期收敛）
- 指令一直不来，超时回到待机
- 确认只生效一次（防重复点击）

**改稿后不能丢失读者位置。** 这是必需项：改一句话把人踢回脚本开头是不可接受的。

安全词电平指示常驻在快门行旁边，让用户知道麦克风在听。

### 4.5 素材归档

- 停止录制后**自动**保存到系统相册，不加确认步骤
- 只申请 add-only 相册权限（弹窗最轻，且不受"仅选中照片"受限访问影响）
- 成功后删除临时文件（相册是唯一归属，不占沙盒）
- **失败时保留临时文件**，并在 HUD 明说失败原因
- 权限在进入录制页时就问，不等到第一次保存——录完才发现被拒会白费一条素材
- 连续多条素材按录制顺序逐条归档

### 4.6 脚本管理（三端职责）

| 端 | 职责 |
|---|---|
| **Web** | 主要的稿件编写控制台，长文本编辑 |
| **iOS** | 浏览 / 选择 / 同步 / 录制 / 安全词小范围修改 |
| Backend | 存储 + 权限 |

iOS **不做**完整文本编辑器。

**版本冻结**：录制开始时冻结 `script_id` + `script_version`。Web 端可能在 iOS
正在录制时改稿，冻结保证录制中的 session 不被远端更新打断。安全词的修改先落在
本地 revision，结束后再合并回云端。

## 5 · 明确不做的

- 定速滚动模式 / 手动 WPM 滑杆。实测语速 + 前推上限已经覆盖"识别不给力"的场景。
- 像素级连续滚动。已确认走整行吸附。
- 提词器跟随状态的常驻文案（「正在跟随」/「已停止」）。高亮停住就是反馈；真正的
  失效（权限、启动失败）已有独立提示通路。
- iOS 端的长文本编辑器。
- 多机位 / 导播。

## 6 · 当前版本状态

### 已实现且有离线验证

- 相机全部档位与前后切换，镜头档位按机型能力计算
- 提词器固定行窗 + 实测语速配速 + 中英排版规则
- 语音跟随算法（中英双语，含全部 §4.3 的对抗场景）
- 安全词 + 改稿指令（含中文指令），改稿后保持读者位置
- 素材自动归档到系统相册，含全部失败分支
- 登录 → 脚本列表 → 录制页 全链路在模拟器跑通

**235 条离线场景**全过（详见技术文档 §10）。

### 未验证 / 未实现

| 项 | 说明 |
|---|---|
| **真机语音链路** | 麦克风、AVAudioSession、录像音轨、按语种选识别 locale 全部接好，但**从未在真麦克风上跑过**。真实口音、噪音、识别延迟的影响只有真机念稿才知道。**这是目前最大的未知。** |
| 三个手感常量未调 | `rateSmoothing` 0.25 / `lookaheadInLines` 1.2 / `correctionGain` 0.25 都是初值，各有离线场景兜底，需真机手感校准 |
| iOS 未接真实 Supabase | 走 `MockBackendClient` 内存实现，接口已就位 |
| 语音指令只实现改段落 | 其余指令类型已在模型里建好但未实现 |
| 提词器显隐未接 UI | `setVisible` 无调用方 |
| 日文脚本 locale 错误 | 日文稿被路由到英文识别器，识别出来是噪声（独立缺陷，处理中） |
| 无 Xcode test target | Swift Testing 版本的用例已写好，但工程里还没加 test target；离线 harness 是当前的验证主力 |

## 7 · 待决产品问题

1. **真机手感之后，配速三个常量取什么值**？需要真人念稿才有答案。
2. **日文/韩文要不要支持**？现在的语种判定只有 CJK/拉丁两分，而识别器需要更细的
   区分（日文喂给中文识别器和喂给英文识别器一样是噪声）。
3. **字号上限档（28pt）下拉丁文 6 行会到 312pt**，接近人脸带。是否要按语种收窄
   上限？
4. **安全词是否允许自定义**？现在硬编码 `Pollux`。
