# 「新闻 → 口播稿」调研管线 — 设计

日期：2026-09-17
状态：待确认

## 1 · 问题

Pollux One 现在的 Script 只有一种诞生方式：人在 Web 上手写
（`web/app/scripts/actions.ts:8` 的 `createScriptAction` 只接受一个 title）。
口播博主真实的工作流不是这样的——他刷到一条新闻，想播，然后要花一两个小时
查背景、核事实、写稿、删到 80 秒。这段时间里新闻已经凉了。

市面上的工具分成两半，没有一个落在中间：

- **通用 AI**（秘塔深度研究、Kimi、豆包）调研强，但产出的是报告不是稿，
  语体、时长、气口全要人工再加工一遍。
- **创作者工具**（度加「热搜一键成稿」、剪映、万彩）出稿快，但本质是热搜标题
  扩写，**没有料可挖**，事实密度接近零。

两边共同缺的是**可信度**。没有一个产品能让博主指着某一句说"这句我有三个独立
信源"。而时政财经口播最大的恐惧恰恰是翻车——翻一次，账号就没有第二次了。

Pollux One 有一件别人做不到的事：**出稿之后不断档**。稿子生成即知道要念多久、
念到哪一句，直接进已有的固定行窗提词器开拍
（`docs/superpowers/specs/2026-08-31-teleprompter-fixed-window-pacing-design.md`）。
所有竞品在"出稿"那一刻就结束了。

## 2 · 已确认的产品决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 入口 | 用户给一条新闻 | 选题仍是用户的事。热点推送和事件监测是后续演进，不在 V1 |
| 输入形态 | **只有两类：文本、图**。链接是文本的子情况 | 分类是管线的活，不是用户的活。用户不该在打字之前先替我们分类 |
| 最快入口 | **Share Extension** | 刷到就分享，学会一次再也不用打开 App。应用内粘贴是兜底不是主路 |
| 端 | **iOS 优先**，手机上一条龙 | 「直拍」场景就在手机上。Web 后续跟上，共用同一套后端 |
| 稿件规格 | **拨盘：时长 × 调性**，时长 0:30–6:00，调性 八卦↔专业 | 见 §2.2 |
| 调研深度 | **不是用户选项**，由拨盘推导 | 用户该想"我要做个什么样的视频"，源的数量是我们的活 |
| 稿件附带 | 每句挂信源 · 时长估算 · 气口标记 | 标题和封面文案不做——与「直拍」闭环无关 |
| 计费 | **token 是一等产品对象** | 见 §10 |
| 不做 | 时政类新闻 | 国内 AIGC 生成时政内容有资质红线。首发切财经/科技/体育/消费 |

### 2.1 一条被物理逼出来的架构约束

调研要 5–10 分钟。iOS 前台任务活不了这么久，API key 也不能落客户端。
所以**没有选择**：iOS 发起 → 后端跑 → 完成推送 → 点开即拍。
这不是一个设计决策，是一个事实。

### 2.2 拨盘：时长 × 调性

原来这里写的是「60–90 秒快评，单一规格」，理由是"单一规格才能把质量调到开箱即用"。
**这条被推翻了。**

用户在 ② 确认页面对的是一个二维取景框（`FocusReticleView` 那套语言）：

- **横轴**：八卦 · 通俗 · 平实 · 偏专业 · 专业
- **纵轴**：0:30 · 0:45 · 1:00 · 1:30 · 2:00 · 2:30 · 3:00 · 4:00 · 5:00 · 6:00

这两个设定**推导出**源数量、事实点数量、调研时长和 token 预算，实时显示在盘下。
「深度/快速」两个按钮消失了——它们是在让用户替我们做我们该做的判断。

**代价要认：** 成稿那一步现在要在整个二维空间里都好用，而不是把一种稿子调到极致。
最难的两个角是 **6:00 专业**（14 个事实点还不能注水）和 **0:30 八卦**（语体和专业
完全是两套写法）。

**应对：V1 只调好两个锚点**——`1:00 通俗` 和 `3:00 偏专业`，其余位置按插值走。
这两个锚点**在盘面上是可见的卡点**，用户看到的是"推荐档位"，我们看到的是"这两格
质量有保证"。产品承诺和工程节奏第一次落在同一个东西上；真发现某个角撑不住，
可以收窄盘面的可达范围而卡点不动，用户不会察觉退让。

### 2.3 口述输入带来的第三个维度

口述档（`说给我听`）比链接档多给一样东西：**角度**。
「央行降准那条，我想从房贷角度切」——后半句链接永远给不了。

所以 `BriefInput` 带一个可选的 `angle`。链接/截图路径为空，口述路径自然填上，
⑥ 选点把它当**软约束**：80 秒装 4–6 个事实点，有了角度就不是模型瞎猜编辑意图。

技术上几乎白送——`SpeechRecognitionService` 已经在 `Engines/` 里跑着，
现在只是把它从"录制中对齐"多接一个"录制前输入"的用法。同一个引擎，两个场景。

## 3 · 最关键的设计：哪里不用 AI

管线有九个阶段，其中**三个刻意不用 LLM**：

```
①抓原文  ②扩展检索  ③抽事实  ④归并  ⑤交叉验证  ⑥选点  ⑦成稿  ⑧挂信源  ⑨时长气口
   ↑         ↑         ↑       ↑        ↑         ↑      ↑       ↑        ↑
 抓取      侦察兵     苦力    代码    代码+苦力    主编   主编    代码     代码
```

④ 归并、⑧ 挂信源、⑨ 时长气口全部是确定性代码，⑤ 交叉验证的计数部分也是。

**正因为"每句挂信源"是查表查出来的、"独立源计数"是算出来的，产品才敢写
"每一句都可溯源"。** 如果这几步交给模型自觉，那句话就是虚假宣传。这是本设计
与"把链接丢给一个带搜索的 agent 让它自己查自己写"之间唯一的实质区别，也是
整个功能的护城河所在。

任何后续改动如果把 ④⑤⑧⑨ 中的任何一步替换成"让模型判断"，都是在拆护城河。

## 4 · 架构

### 4.1 数据流

```
用户粘一条新闻
  │
  ├─► Brief（任务）── 阶段状态机，每阶段结果落库
  │     │
  │     ├─ Source[]   抓到的信源：URL · 正文 · 发布方 · 发布时间 · 内容指纹
  │     ├─ Fact[]     从单个 Source 抽出的原子事实，带逐字引文 + source_id
  │     ├─ Claim[]    归并后的事实点，带 supporting_sources + independence
  │     └─ Verdict    Brief 级结论：能不能播
  │
  └─► Script（已有类型）+ ScriptEvidence（新）
        │                    sentence_id → claim_ids
        └─► 现有提词器 / 录制闭环，一行都不用改
```

**Script 是已有类型，不改。** 管线的终点就是往 `scripts` / `script_sections` /
`paragraphs` / `sentences` 写入一条正常的 Script。证据层挂在旁边
（`script_evidence`），提词器完全不需要知道它存在。

**但"录制侧零改动"是不成立的**——这条曾经写在这里，查过代码之后收回。
五处接缝见 §9.2。

### 4.2 阶段状态机（而不是一个长任务）

5–10 分钟的任务不能是一次函数调用。拆成**九个各自 < 60s 的阶段**，
由一张 `brief_stages` 表驱动，runner 反复唤醒、每次推进一个阶段。

好处不只是能跑在 serverless 上：

- **可观测**——iOS 能实时显示"正在交叉验证第 6 个源"，5 分钟的等待不再是黑盒
- **可重跑**——某阶段失败只重跑那一阶段，不用重头挖 12 篇全文
- **可换模型**——每阶段独立配置 model，Pro 版只是换一张配置表

这与 `Engines/` 下每个 Engine 严格单一职责（`CameraEngine` 不理解 Script、
`ScriptAlignmentEngine` 不理解 UI）是同一套品味。

### 4.3 各阶段分工

| 阶段 | 执行者 | 说明 |
|---|---|---|
| ① 抓原文 | 抓取库；截图输入用 `deepseek-flash` | flash 原生带视觉。用户从 App 截图分享是必然场景 |
| ② 扩展检索 | 基础版 `deepseek-flash` 生成检索式 + 搜索 API 执行<br>Pro 版 `claude-sonnet-5` + 服务端 `web_search_20260209` | 两版能力差最大处。Sonnet 5 能边搜边判断"这个角度还没覆盖"并自行再搜一轮；DeepSeek 无原生联网，只能一次性生成检索式 |
| ③ 抽事实点 | `deepseek-flash` | 全管线 token 消耗最大的一步（十几篇全文）。1M 上下文一次吃下，输入 $0.15/MTok。**每个 Fact 必须带 source_id + 逐字引文**，这是后面一切的根 |
| ④ 去重归并 | **代码**（embedding 聚类 + 规则） | 说同一件事的 Fact 归成一个 Claim。embedding 走一个独立的小模型接口，与 ①–⑦ 的对话模型解耦 |
| ⑤ 交叉验证 | **代码**（独立源计数）+ `deepseek-flash`（冲突二分类） | 见 §5 |
| ⑥ 选点 | 基础版 `deepseek-v4-pro` / Pro 版 `claude-sonnet-5` | 80 秒只装得下 4–6 条。取舍是编辑判断力 |
| ⑦ 成稿 | 同上 | 见 §6 |
| ⑧ 挂信源 | **代码**（查表 + 校验） | 见 §6.2 |
| ⑨ 时长气口 | **代码** | 见 §7 |

角色可以这么记：**一个苦力**（flash，读全文抽事实，量大管饱），
**一个侦察兵**（带搜索的模型，找料），**一个主编**（强模型，取舍和落笔）。

## 5 · 独立源计数（护城河的核心）

"有几个信源"这个数字如果算错，整个可信度承诺就是假的。**同一家通讯社的稿子被
5 家门户转载，不是 5 个源，是 1 个。** 这是最容易出错也最致命的地方。

判定两个 Source 不独立，满足任一即可：

1. **正文指纹相似**——5-gram shingle + MinHash，Jaccard ≥ 0.5 判为同源（起始值，需用真实转载样本调参）
2. **显式转载标注**——正文含"来源：XX社"「据XX报道」且指向另一个已收录 Source
3. **同一媒体主体**——同域名，或落在同一媒体集团映射表里

归并后每个 Claim 得到一个 `independence`：互不相关的 Source 组数量。

**归并的同时必须留下 `merged_away_count`**——被判为转载而归并掉的篇数。归并是有损
操作，只保留 `independence` 就等于把这个数扔了，而它正是用户在审稿页看到的第二个
数字：

> 3 个独立信源
>
> 另有 6 篇为上述稿件转载，未计入

两个数要分开存、分开显示。合并成一个就只剩上面那行，用户无从知道我们到底看过多少
篇、剔掉了多少篇——而「剔掉了 6 篇」本身就是可信度的证据。反过来，把两者相加
（3 + 6 = 9 个源）恰恰是本设计最怕的那种误读，也正是 §5 开头那句"5 家门户转载不是
5 个源"要防的事。这一列因此必须独立存在——`brief_claims` 上要多一列
`merged_away_count`，§9 那张表相应补上——不能在算完 `independence` 之后顺手丢掉。

由此定义 Claim 的 `confidence`：

| confidence | 条件 | 处理 |
|---|---|---|
| `strong` | independence ≥ 3 | 可进稿，正常呈现 |
| `weak` | independence 1–2 | 可进稿，但稿中标黄，审稿页提示"单一信源，未交叉验证" |
| `conflicted` | 源之间事实冲突 | **不进稿**，单独列出冲突双方，让用户自己决定 |

冲突检测是唯一需要语义判断的部分——两条 Claim 是否互相矛盾，交给
`deepseek-flash` 做二分类。计数部分全是算术。

### 5.1 产品必须敢说"这条别播"

如果 `strong` 的 Claim 少于 3 条，**不出稿**。Brief 以 `insufficient` 结束，
iOS 展示一页结论：查到了什么、为什么不够、冲突在哪。

这个门槛与 §2.2 的拨盘无关——**无论拨到哪一档，都要至少 3 条 strong 打底**，
其余名额才可由 `weak` 补足（标黄呈现）。一篇全靠单一信源撑起来的稿子不该存在。
拨到 6:00 专业却只有 3 条 strong，同样是 `insufficient`：时长是用户的期望，
不是我们伪造事实的理由。

这是"敢播"承诺的另一半。不敢播的时候必须拦住用户——硬憋一篇稿出来，
第一次翻车就没有第二次了。

## 6 · 成稿与信源绑定

### 6.1 输入受限

⑥⑦ 阶段的模型**只能看到通过 ⑤ 验证的 Claim 列表**，每条带 ID。它看不到原始
网页，也看不到被否掉的 Claim。这样模型无法"顺手补充一点背景知识"——那些
补充恰恰是最容易出错、也最无法溯源的部分。

### 6.2 schema 强制映射

成稿用 structured output（`output_config.format` + `strict: true`），每个句子必须声明：

```
{ "text": "...", "kind": "fact" | "opinion" | "transition", "claim_ids": [...] }
```

⑧ 阶段是纯代码校验：

- `kind: fact` 而 `claim_ids` 为空 → **拒绝，重跑 ⑦**（这句是模型自己编的）
- `claim_ids` 里出现未通过验证的 ID → 同上
- `kind: opinion` 带 claim_ids → 剥离（观点不该伪装成有据可依）

**⑧ 的产物不止句子级映射，还有句内字符区间。** 除了 `sentence_id → claim_ids`，
每条挂接还要落一对位置：

```
{ "sentence_id": "...", "claim_id": "...", "start": 8, "length": 6 }
```

`start` / `length` **以 Character 计，不是 UTF-16 code unit**——中文一个字算一个。
这不是洁癖：用 UTF-16 的话，一句话里只要有中文，后面每一条下划线都会整体错位，
而且越往后错得越多。

这条要求是从已定稿的 mock 反推出来的：审稿页里那些虚线下划线（`0.5 个百分点`、
`3 月 15 日`）画在哪几个字底下，靠的就是这对数字。原先只写句子级映射，界面能画的
就只有整句下划线——一句话里究竟哪几个字有据可依、哪几个字是模型自己的措辞，用户
看不出来，而这正是"每句可溯源"里最有说服力的那一半。`script_evidence` 因此要多
`start` / `length` 两列，§9 那张表相应补上。

一个句子可以有多个锚点，指向同一条或不同的 Claim。区间越界或彼此重叠一律算 ⑧ 校验
失败，该句退回无锚点的纯文本——**画错位置的下划线比不画更糟**，它会让用户点开一个
数字，看到的却是另一件事的信源。

**事实句与观点句的区分本身就是产品功能。** 审稿页里两者视觉不同：事实句可以
展开看信源，观点句明确标为"你的判断"——让博主清楚知道哪几句是他要自己负责的。

## 7 · 时长与气口（用你独有的数据）

秒数不靠模型估，靠**该用户真实语速**。

⚠️ **原文在这里写错了一句**：说 `ReadingProgress` 上报链路"已经在产生这个数据，
只是还没有人用"。**没有。** 详见 §9.2 ①——这份数据目前根本不存在，要新建。

- 有历史数据：取该用户**近 10 次**录制的中位 charsPerSecond（中位而非均值——一次结巴的 take 不该拖慢全局）
- 新用户：按语种默认值（`ScriptLanguage` 已有中英分流）

气口按标点和句法切：句末标点 = 长气口，句中逗号/顿号 = 短气口。
这些落在 Sentence 的元数据上，提词器的固定行窗配速可以直接消费。

竞品做不出这个——他们没有用户真实语速。

## 8 · iOS 侧：重划一条边界

README 现在写的是「Web 是主要的 Script Management Console，iOS 只负责浏览 /
选择 / 同步 / 录制 / Safe Word 小范围修改」。iOS 优先意味着这条线要重画。

新的边界是：**Web 撰写，iOS 审稿。**

| | Web | iOS |
|---|---|---|
| 自由长文本编辑 | ✅ | ❌（仍然不做） |
| 发起 Brief | ✅（后续） | ✅ |
| 看 Brief 进度 | ✅ | ✅ |
| 审稿：逐句看信源 | ✅ | ✅ |
| 审稿：删句 / 接受 / 改几个字 | ✅ | ✅ **新增** |

"审稿"是句子粒度的接受/删除/微调，不是一个文本编辑器。这条线能守住：
iOS 上永远不会出现一个空白的多行输入框。

七个界面，mock 已定稿：https://claude.ai/artifact/X3Jiga6RWyGyEhkstrPBEn
（① ② ③ ④ 可交互：档位切换、拨盘拖拽、左滑操作、屏间跳转）

1. **① 相机（根）**——已有界面。右下角那格随 `hasScript` 变
2. **② 当前稿件详情**——即下面的"审稿"，同一个 View
3. **③ 交给我**——`打字 / 说给我听` 两档。打字档是一个输入框（链接与文本合一），
   剪贴板检测是输入框上方的快捷条、未授权则整条不出现；`上传截图` 与 `分享进来`
   并列在下方——它俩是一类：东西在别处
4. **④ 确认**——新闻收成一行标签，拨盘是主角（§2.2）
5. **⑤ 等待**——顶部 1/3 是 token 表，下方九个阶段带**计数**而非耗时
   （14 篇 · 86 条 · 23 点）——计数告诉用户挖到了什么，那才是他愿意等下去的理由
6. **⑥ 不建议播**——§5.1 的可见形态
7. **⑦ 换一篇**——历史稿件，次要路径

### 8.1 句子级操作按类型分化

④ 审稿页每句可左滑。**露出的按钮由句子类型决定**：

| 句子 | 露出 |
|---|---|
| 事实句 | `重查信源` + `删除` |
| 钩子句、观点句 | 只有 `删除` |

观点句没有信源可重查，给它一个"重查"按钮就是在骗人。这个分化是从 §6.2 的
`kind` 字段长出来的，不是排版决定。

### 8.2 返回语义分层

每一屏的"返回"含义不同，这是本设计里最容易做错的交互：

| 屏 | 返回去哪 | 语义 |
|---|---|---|
| ② 确认 | ① | 还没花钱，纯粹的后退 |
| ③ 等待 | ① | **「离开」不是「取消」**——任务继续在云上跑 |
| ④ 审稿 | ① | **回不到 ③**，调研已结束，那一屏不复存在 |
| ⑤ 不足 | ① | 同上 |

**② → ③ 是一条不可逆的边界**，因为过了这条线开始烧 token。所以 ③ 的返回必须是
"离开"——用户随手一按不该毁掉一个已经花了钱的任务。真正的取消是另一个动作，
放在底部做成很轻的一行，并且**明说"已消耗的 48K 不退"**。

## 9 · 数据模型

新增表，全部带 `user_id` + RLS，与现有表一致：

```
briefs           id · user_id · input_kind · input_payload · angle
                 duration_sec · register · status · verdict
                 tokens_budget · tokens_used · cost_cents · created_at
brief_stages     id · brief_id · stage · status · started_at · ended_at · error · result
brief_sources    id · brief_id · url · publisher · published_at · body · fingerprint
brief_facts      id · brief_id · source_id · text · quote · extracted_at
brief_claims     id · brief_id · text · independence · confidence
claim_facts      claim_id · fact_id                         （多对多）
claim_conflicts  claim_id · conflicts_with                  （谁和谁冲突）
script_evidence  sentence_id · claim_id · sentence_fingerprint （⑧ 的产物）
sentence_breaths sentence_id · kind · char_offset           （⑨ 的产物，一句多行）
```

`briefs.input_kind`：`text` ｜ `image`（**只有两类**——链接由 ① 抓原文自己判断
"这坨文字里有没有 URL"，不让用户先替我们分类）
`briefs.register`：0.0（八卦）– 1.0（专业）
`briefs.status`：`queued` → `running` → `drafted` → `confirmed` ｜ `insufficient` ｜ `failed` ｜ `canceled`

`brief_stages.result` 里各阶段分别记自己的 token 消耗，③ 等待页的分色堆叠条直接读它。

三处和本节初稿的出入，都是实现时想清楚后有意改的：

- **`claim_facts` 而不是 `claim_sources`**。Claim 是由 Fact 归并出来的，独立源要
  顺着 fact → source 走一遍才算得出。直接存一份 source 列表就多了一个会和事实
  对不上的副本。
- **`claim_conflicts` 是新加的**。只在 claim 上记一个 `confidence = 'conflicted'`
  不够用：⑥「不建议播」那屏要把冲突双方并排摆出来（路透 23 亿 vs 彭博 31 亿），
  光知道「这条有冲突」渲染不出来。
- **`sentence_breaths` 一句多行**，不是 `sentence_prosody` 一句一行。⑨ 对每个句内
  逗号都产出一个带位置的短气口、句末再产出一个长气口；做成每句单个枚举的话那一列
  永远只会是 `long`，而提词器真正用来配速的句内短气口全部无处可去。重读
  （emphasis）目前没有任何代码产出，等有了再单独建表。

Brief 产出的 Script 走现有表，不加字段。`script_evidence` 挂在旁边，
提词器和录制侧完全不需要知道它存在。

### 9.1 iOS 抽象层

`BackendClient` 协议加三个方法，保持"没有任何类型提到 Supabase"这条纪律：

func estimateBrief(durationSec: Int, register: Double) -> BriefEstimate   // 纯函数，本地算
func accountBalance() async throws -> TokenBalance
func createBrief(input: BriefInput) async throws -> Brief
func observeBrief(id: UUID) -> AsyncStream<Brief>      // 阶段进度 + 实时 token

`MockBackendClient` 同步实现一个带假阶段推进的版本，让整条 UI 在没有后端时
也能跑通——与现有 V1 的做法一致。

### 9.2 与现有录制闭环的接缝

§4.1 原本断言"录制侧零改动"。查过代码之后：**提词器确实不用改，但有五处接缝。**

#### ① 语速数据不存在，必须新建

`ReadingPacer.rate`（`ios/Pollux One/Engines/ReadingPacer.swift:31`）确实是字符/秒，
但它是**会话内状态**，`reset()` 就没了。而 `script_reading_progress` 和
`reading_sessions` 两张表只有 `completed_sentences` / `total_sentences` /
`fraction_complete`——**没有任何速率字段**。

所以"按你的语速"这条差异化**目前没有数据支撑**。第一段实现要补：

- take 结束时导出 `ReadingPacer.rate`，带语种和置信度（`minimumRateConfidence = 0.5`，
  低于门槛的 take 不计入）
- 新建 `user_reading_rates`（`user_id · language · chars_per_second · sample_count · updated_at`），
  §7 说的"近 10 次中位"从这里取

这也意味着**新用户的第一篇稿必然用语种默认值**——差异化要等几次录制之后才生效。
产品文案不能上来就说"按你的语速"。

#### ② 根视图要倒过来，相机不能再"属于某一篇稿"

原文写的是"审稿插在列表和 RecordingView 之间"。**这句作废了**——那还是把脚本列表
当主干的思路，与 README 第一句「Camera first」相反。

新结构：

```
① 相机（根）──有稿──→ ② 当前稿件详情 ──开拍──┐
     │                                          │
     └──无稿──→ ③ 交给我 → ④ 确认 → ⑤ 等待 ────┘
                                          落回 ②
```

- 相机右下角那格**随状态变**：有稿 → 当前稿；无稿 → 直接去「交给我」
- **审稿页就是稿件详情页**，一个 View 两个入口（相机进 / 调研完成落回）。
  原先画成两屏是按"新建流程"和"管理流程"分的，那是后台系统的思路
- `ScriptListView` 降级为「换一篇」，只从详情页进，**不在主路径上**——
  低频的东西不该挡高频的路

代码上要动三处，一处比一处深：

1. **`App/RootView.swift:9` 挂的是 `ScriptListView`**，改挂 `RecordingView`。
2. **`RecordingView.script` 是 `let script: Script`**（`Features/Recording/RecordingView.swift:14`），
   不可选、构造时注入。相机作为根视图必须能在"没有稿"时运行，这个字段要变成
   `Script?`，提词块整块随之隐藏。
3. **最麻烦的一处：`RecordingView.init` 每次构造都造一个新的 `SessionManager`**
   （`RecordingView.swift:50`）。

   这一条前一稿写的是"`SessionManager` 按 script 造出来"、"`scriptRevision` 要改成
   可选"——**对着代码核过，两句都不对**：

   - `SessionManager.init` 的签名是 `init(syncService:alignmentEngine:takeArchiver:)`，
     **它根本不接受 script**。稿子是之后由 `prepare(script:)` 装进去的，而且那是个
     **async** 方法。
   - `scriptRevision` **本来就是** `private(set) var scriptRevision: ScriptRevision?`，
     不存在"要改成可选"这回事。

   真正的毛病在**谁持有它**：`SessionManager` 归 `RecordingView` 所有，`CameraEngine`
   又在 `SessionManager` 的 init 里造一次。于是从列表进另一篇稿 = 新的 `RecordingView`
   = 新的 `SessionManager` = 新的 `CameraEngine`，用户会看到取景器黑一下重启。
   换句话说，**相机会话的生命周期被绑在某一篇稿上**，不是因为引擎不会换稿，而是因为
   View 的构造顺手把它一起重建了。

   引擎层其实**已经支持**换稿（`prepare(script:)` 内部就是 `teleprompterEngine.load` +
   `alignmentEngine.reset`），**错的是持有者和构造时机，不是能力**。
   结论不变：把 `SessionManager` 提到 `RecordingView` 之上（由 `AppEnvironment` 或一个
   相机场景对象持有），`RecordingView` 只订阅它，换稿走一次 `await prepare(script:)`。

顺带两条：

- 「换一篇」的数据源是 **Brief + Script 的合并流**——Brief 在跑的时候还不是 Script，
  `viewModel.scripts` 装不下它
- 空状态文案 `"Write a script on the Pollux One web console, then pull to refresh."`
  在 iOS 优先之后是错的

#### ③ Safe Word 会让信源对不上（最危险的一处）

录制中 Safe Word 改段落走 `SessionManager.applyParagraphReplacement` →
`BackendClient.updateParagraph`。句子文本变了，但 `script_evidence` 还指着那个
`sentence_id`——**信源凭空挂到了一句用户临场改过的话上**。这恰好摧毁"每句可溯源"
的承诺，而且是在最不容易被发现的地方。

处理：`script_evidence` 带上写入时的**句子文本指纹**。文本一变，该句降级为
"已改动 · 无信源"，而不是继续显示旧信源。审稿时删句同样要清理孤儿 evidence。

#### ④ 文本拼接必须走 `PromptScriptText`

`Paragraph.fullText` 用 `" "` 连接（中文会多一个半角空格），`Token.tokenize` 按空格切。
teleprompter spec 已写明"这次不改它"，并警告过**两边各拼一次会让字偏移永久性偏移且随
脚本长度累积**。

管线落库的只是句子文本，**排版口径仍由 `PromptScriptText` 唯一持有**，管线不得自己拼一遍。

#### ⑤ 气口标记放哪：一个必须承认的矛盾

`Sentence` 是 `id/order/text/tokens`，`sentences` 表是 `id/paragraph_id/sort_order/text`。
"Script 不加字段"和 §7 的"气口落在 Sentence 的元数据上"**不能同时成立**。

决定：另建 `sentence_breaths`（`sentence_id · kind · char_offset`），和
`script_evidence` 一样挂在旁边。提词器要用时才读，不用时 Script 仍然是干净的。

**一句多行**：⑨ 对每个句内逗号都产出一个带位置的短气口，句末再产出一个长气口。
表上用一条 check 约束把这个判别联合固化下来——short 必须带位置，long 必须不带。

## 10 · 成本与计费

### 10.1 token 是一等产品对象

这一层原 spec 完全没有。产品跑在云上、按 token 计费，那 token 就不该藏在设置里。

| 时机 | 呈现 |
|---|---|
| **花钱之前**（② 拨盘） | 盘下实时显示 `≈120K · ¥0.35`。**余额买不起的区域直接画在盘面上**——按每一档时长分别算出能走到多右，所以边界是锯齿状的，如实反映"时长越长，能承受的专业度越低"。拖进去：读数变警示色，按钮变"余额不够，去充值"且不可点 |
| **花钱之中**（③ 等待） | 顶部 1/3 的 token 表：实时读数、折人民币、按环节分色的堆叠条（抽取/成稿/检索用**同一色相的三个明度**，不能碰 ④ 的语义色）、预算与本月余额 |
| **中途放弃** | 取消时**明说已消耗的不退** |

分环节的数字不只是好看，它把成本结构摊开了：抽取吃掉约 80% 的 token，成稿只占
13%。将来要压成本，一眼知道该动哪里。

**「本月余额」是账户级的数，不属于任何一篇 Brief。** 它由 §9.1 的 `accountBalance()`
给出——本月额度减去本月已消耗——与单篇的 `tokens_budget` / `tokens_used` 是两套数，
不能互相推算。等待页把两者并排摆着（`预算 120K · 已用 40%` 和 `本月余额 2.41M`），
是因为用户在那一屏真正想知道的不是这一篇花了多少，而是"照这个烧法这个月还够不够"。

**余额门禁放在 ④ 确认页**（上表"花钱之前"那一行，按旧编号写作「② 拨盘」，是同一屏）。
判断只有一句：**预估 token 超过本月余额，就不许创建 Brief。** 不是创建完再提示，是
在创建之前拒绝——按钮变成"余额不够，去充值"且不可点，并给出差额（"这一篇大约要
120K，你只剩 80K"）。这也是 §2.2 拨盘上那块"买不起的区域"的判据，两者用同一个
`estimateBrief` 结果。

这一条与上面的**软预算**不冲突，两者管的是不同的事：软预算管**单篇跑超了自己的
预估**——超了不停，如实结算；门禁管**账户根本付不起这一篇**——那就必须拦在花钱之前。
九个阶段跑完才发现付不起，token 已经烧掉了，退不回来，而这一屏是烧钱之前的最后一屏
（§8.2 说的那条不可逆边界就在它之后）。§11 的"余额门禁"那一行测的就是这件事。

两个还没定的问题：

- **超预算怎么办**——倾向**软预算**：超了不停，表上变色提示，结束后如实结算。
  硬停会在最难受的时刻打断用户
- **估算函数的准确度**——`estimateBrief` 是本地纯函数，必须跑真实样本回归校准；
  估低了用户会觉得被骗

### 10.2 单篇成本

粗估，单篇 80 秒稿 / 12 个源：

| | 基础版（DeepSeek） | Pro 版（Claude Sonnet 5） |
|---|---|---|
| 抽事实 | ~$0.014 | 含下方 |
| 验证 | ~$0.005 | — |
| 成稿 | ~$0.008 | — |
| 搜索 API | ~$0.005–0.01 | 含工具调用 |
| **合计** | **约 $0.03–0.05（¥0.25–0.4）** | **约 $0.25–0.4（¥2–3）** |

两个必须做的省钱动作：

- **开缓存**。口播语体规则和各阶段系统提示词是固定的，DeepSeek 缓存命中
  $0.003–0.006/MTok，比未命中便宜约 50 倍
- **谷时排队**。DeepSeek 有峰谷价差，谷时约半价。不紧急的 Brief 可以排到谷时跑

模型 ID 记录在案（会变，实现时复核）：`deepseek-flash`（V4.1-Flash，1M 上下文，
原生视觉）、`deepseek-v4-pro`、`claude-sonnet-5`（1M，$2/$10，服务端
`web_search_20260209`）。**DeepSeek API 无原生联网**，基础版必须外挂搜索 API（候选：博查 Bocha、
火山方舟带联网的 Bot API、Tavily）。搜索层做成可替换接口——这样 Pro 版切到
Claude 原生 `web_search` 时，只是把 ② 阶段整个换掉，③–⑨ 一行不动。

## 11 · 测试

| 层 | 测什么 |
|---|---|
| 独立源计数 | 构造"1 篇通讯社稿 + 5 篇转载"，必须判成 independence = 1。这是最关键的单测 |
| 冲突处理 | 构造互相矛盾的两组源，Claim 必须落到 `conflicted` 且不进稿 |
| 不足降级 | 只喂 2 个源，Brief 必须以 `insufficient` 结束，不出稿 |
| schema 校验 | 喂一个 `kind: fact` 但 `claim_ids` 为空的模型输出，⑧ 必须拒绝并触发重跑 |
| 阶段状态机 | 单阶段失败后重跑，不重复消耗前面阶段 |
| 时长估算 | 有历史语速 / 新用户两条路径 |
| 成本估算 | `estimateBrief` 在拨盘四个角的输出，与真实样本的实际消耗对比，偏差记录在案 |
| 余额门禁 | 余额低于估算时，Brief 必须在创建前被拒，不能已经烧了 token 才发现 |
| 两个锚点 | `1:00 通俗` 与 `3:00 偏专业` 各跑一批真实新闻，人工评稿件质量——这是 §2.2 的验收条件 |

前四项不需要调用任何模型——喂固定的中间态数据即可。这是拆成阶段的直接收益：
**管线最关键的逻辑全部可以离线测试。**

## 12 · 实现顺序

⚠️ **本节的顺序在动手时被推翻了。** 下面写的是"先做后端管线、跑完质量关再投界面"，
实际执行的是反过来：**先用 fixture 把七个界面立起来，全程零网络、一次模型调用都不发**，
再去接真实管线。两份计划分别是：

- 先做 `docs/superpowers/plans/2026-09-18-brief-ios-on-fixtures.md`（界面喂 fixture）
- 后做 `docs/superpowers/plans/2026-09-18-brief-live-pipeline.md`（①–⑨ 真实管线）

**质量关是推迟，不是取消。** 界面这一段做完，"稿子到底好不好、信源挂得准不准"仍然
一个字都没回答；下面第二段那句"在 `1:00 通俗` 和 `3:00 偏专业` 两个锚点上各评一遍
稿件质量"照样要过，只是挪到了界面之后。这个代价必须记在明面上，否则七个界面点起来
很顺，容易让人以为产品已经成立了。

换来的好处已经兑现：mock 反推出三样确定性内核目前产不出来的东西——§6.2 的句内字符
区间、§5 的 `merged_away_count`、§10.1 的本月余额与余额门禁。这三样若等管线建完再
发现，改动要横穿 schema、后端和界面，贵得多。界面先行的价值就在这里，不在"先看到
东西"。

以下是原定顺序，除被上面推翻的先后之外，内容仍然有效：

这个 spec 的体量适合拆成两个实现计划，中间有一个天然的验证点：

**第一段：后端管线（①–⑨）。** 不碰 iOS，用一个命令行脚本喂进一条真实新闻，
跑完输出 Script + 证据层的 JSON。这一段做完就能回答唯一重要的问题——
**稿子到底好不好、信源到底挂得准不准**。好不了的话，界面做得再顺也没用。

**第二段：iOS 七个界面 + Share Extension。** 建立在已验证的管线上，mock 已定稿
（https://claude.ai/artifact/X3Jiga6RWyGyEhkstrPBEn），不需要再做设计探索。

这一段的第一件事不是画界面，是 §9.2 ② 的第 3 条：**把 `SessionManager` 从
`RecordingView.init` 里提出来**。相机不能再属于某一篇稿，否则换稿就闪一下——
这个结构不先理顺，后面每一屏都会被它拖着。

先做第一段，用真实新闻跑一批样本，**在 `1:00 通俗` 和 `3:00 偏专业` 两个锚点上
各评一遍稿件质量**（§11 的最后一行），再决定要不要投第二段。

§9.2 ① 的 `user_reading_rates` 也要在第一段做——它在 iOS 侧采集，但没有它
§7 的时长估算只能退回语种默认值，两个锚点的稿件质量就评不准。

第一段里 §10.1 的 `estimateBrief` 必须一起做——它是纯函数，但它的系数只能从
真实样本的实际消耗里回归出来，而那批样本正好是第一段产出的。

## 13 · 明确不做

- 标题、封面文案
- 数字人、配音、剪辑合成——红海且被字节/百度免费化，将来接第三方 API 即可
- 时政类新闻
- Web 侧的 Brief 发起入口（后端共用，界面 V1 后补）
